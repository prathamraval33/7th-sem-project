# studyresourcerule.md — AI-Curated, Curriculum-Driven Study Resource System

## How to use this document

You are an AI coding assistant implementing a new feature for an existing multi-tenant placement portal (FastAPI + SQLAlchemy 2.0 + PostgreSQL + Alembic backend, React + Vite + Tailwind frontend, Groq API as the AI provider, an existing web-search integration already used for the platform's Career Insights feature). This document is the complete specification for a new feature: a **curriculum-driven, AI-curated study resource system**, where a College Admin uploads their college's actual syllabus/curriculum document, the system extracts real structure from it, TPOs pick which subjects are worth focusing on, AI finds real books/articles/videos for each of those subjects, TPOs review and approve what AI found, and only then do students see it.

Read this entire document before writing any code. This feature touches several parts of the system that already exist (the existing flat Resources/library module, the existing college-scoping/multi-tenant isolation rules, the existing web-search + Groq pipeline used for Career Insights, the existing TPO approval-workflow patterns used elsewhere in this project) and it is important to reuse those existing patterns rather than building parallel new versions of things that already work.

The single most important design principle in this entire document, repeated multiple times below because it is the easiest thing to get wrong: **this feature must work correctly for any college, with any branch names, any number of semesters, and any subject list — nothing about branches, semesters, or subjects may ever be hardcoded anywhere in the schema, the backend, or the frontend.** Every one of those values comes from whatever a specific college's own uploaded document actually says. The college this project originally started with (referred to throughout this project as "BVM") is just the first real college using this system — its branch names (IT, Computer Science, Mechanical, Civil, Electrical) are real data belonging to that one college, not a fixed list the platform assumes applies to everyone.

## PART 1 — Why this feature exists and what problem it solves, explained fully

### 1.1 The problem with the current Resources module
The existing Resources/study-material library on this platform today works like this: a TPO or Admin manually finds a link or uploads a document, manually types a title and description, manually picks a topic tag from a fixed list of pills (Aptitude, Communication, Operating Systems, DBMS, Computer Networks, Java, Python, Interview Q&A), and manually publishes it. This has two real limitations. First, it is entirely manual labor — every single resource a student ever sees had to be personally found and entered by a human. Second, the topic list itself is a flat, fixed set of pills that happens to match what one specific college's curriculum looks like — it has no real relationship to what that college's students are actually studying in which semester of which branch, and it would not automatically make sense for a different college with a different curriculum.

### 1.2 What this new feature does instead, in one paragraph
Instead of a human manually curating every single resource, a College Admin uploads the one document that already exists for every college anyway — their official curriculum/syllabus document, which lists every branch, every semester, and every subject taught in that semester. AI reads that document once and turns it into real, structured data specific to that college. From there, each branch's TPO looks at their own branch's real subject list, and — instead of every subject needing a resource, since some subjects are more relevant to placements and current industry trends than others — picks out the subjects worth focusing on. For each of those chosen subjects, AI does the work a human TPO would otherwise have had to do themselves: searching for good books, articles, and free educational videos about that specific subject, and writing a short summary of what each one covers and why it's worth a student's time. The TPO reviews this AI-curated shortlist (since AI curation, like AI-generated content anywhere in this project, should not be trusted blindly and published straight to students) and approves it. Only after approval does a student see it — and when they do, it's organized exactly the way they'd expect: click on "DBMS," see a curated set of a few good books, articles, and videos specifically about DBMS.

### 1.3 Why this must be general-purpose, not built around one college's structure
This platform is multi-tenant — many different colleges will eventually use it, each with their own real curriculum. Different colleges call their branches different things, some may not even use the word "branch" the same way, some run an 8-semester program and others might structure things differently, and every college's actual subject list is different even within the same branch name. If any part of this feature hardcodes a specific list of branches, a specific number of semesters, or a specific set of subjects anywhere in the schema, the backend logic, or the frontend, it will subtly or completely break the moment a second real college with a different structure starts using the platform. Every single piece of "what branches exist," "how many semesters," and "what subjects are in which semester" must be treated as data extracted from that specific college's own upload, scoped to that college's `college_id`, and never assumed in advance anywhere in the code.

### 1.4 This feature replaces, not adds to, an earlier incorrect assumption
Earlier work on this project's Resources upload form added a fixed set of "applicable branch" pill buttons (IT, CS, Mechanical, Civil, Electrical) for tagging which branches a resource applies to. That was built before this curriculum system existed, and it made the same mistake described in 1.3 — it assumed BVM's specific branch list applied everywhere. Once this feature is built, that hardcoded pill list must be replaced with pills generated dynamically from whatever branches actually exist in that specific college's uploaded curriculum data (see Part 6 for exactly how to make this change). Do not leave both the old hardcoded version and the new dynamic version coexisting — the hardcoded one must be removed as part of this work.

## PART 2 — Curriculum Upload and AI Extraction (College Admin side)

### 2.1 What the College Admin actually does
On the College Admin's dashboard, add a new section/page, something like "Curriculum Setup." Here, the Admin uploads their college's official curriculum or syllabus document — this will most commonly be a PDF, since that is the overwhelmingly standard format colleges already use for this kind of document, but the upload should also reasonably accept common alternatives like DOCX if the underlying text-extraction tooling already available in this project's stack supports it without significant extra work; if not, scope this first version to PDF only and note that as a known limitation rather than blocking on building broader file-format support.

### 2.2 What "AI extracts topics from it" actually means, mechanically
This is not a vague, magical step — it is a concrete pipeline, and should be built as follows:
1. When the Admin uploads the file, extract its raw text content first, using whatever PDF-text-extraction tooling already exists elsewhere in this project (this project already parses PDFs for resume text extraction and for fee-receipt OCR — check whether the same underlying library/approach can be reused here before introducing a new one, since consistency and less duplicated tooling is preferable).
2. Send that raw extracted text to Groq (the same AI provider already used throughout this project) with a carefully constructed prompt instructing it to identify and return a structured breakdown of: every branch/department mentioned in the document, and for each branch, every semester mentioned, and for each semester, the list of subject names taught in it. Instruct the model explicitly to return this as strict, parseable structured output (for example, a defined JSON shape with branches as a top-level array, each containing a semesters array, each containing a subjects array of plain subject-name strings) rather than freeform prose, since this output needs to be reliably parsed by code afterward, not read by a human.
3. Because curriculum documents vary enormously in formatting quality (multi-column layouts, tables, scanned/image-based pages, inconsistent semester labeling, subjects sometimes listed with course codes and sometimes without), do not assume the first extraction attempt will be perfect. Build this as a best-effort extraction that produces a reasonable draft, which is then always reviewed by a human before being saved as real data (see Part 2.4) — do not build this as a fully-automatic, no-review pipeline.

### 2.3 Data storage — general-purpose, per-college, per-branch
Create a new table, something like `curriculum_subjects` (or similar naming consistent with this project's existing naming conventions), with columns: `id`, `college_id` (foreign key, exactly like every other college-scoped table in this project), `branch_name` (plain text — never a fixed enum, since branch names are arbitrary per-college data, not a closed set of platform-wide values), `semester_number` (integer, plain descriptive metadata), `subject_name` (plain text), and a `source_upload_id` (referencing whichever record represents the original uploaded document, so it's always possible to trace which subjects came from which upload, useful if a college later re-uploads an updated curriculum). Every single row in this table must always have a real `college_id` — there is no such thing as a platform-wide curriculum row, since every college's curriculum is entirely their own data, structurally similar to how `drives` and `applications` are already college-scoped in this project.

Also create a record of the upload event itself, something like a `curriculum_uploads` table: `id`, `college_id`, `uploaded_by` (the Admin user), `original_filename`, `uploaded_at`, `extraction_status` (e.g. `processing`, `ready_for_review`, `confirmed`, `failed`), and a raw copy of the AI's extracted-but-not-yet-confirmed structure (e.g. as a JSON column) so the review step (2.4) has something concrete to show and let the Admin edit, before it gets written into the real `curriculum_subjects` table.

### 2.4 The mandatory human-review step — do not skip this
After AI extraction produces its draft structure, do not write it directly into `curriculum_subjects` as final data. Instead, show the College Admin an editable view of exactly what was extracted — every branch, every semester, every subject, presented in a clear, editable list/table interface — with the ability to: fix a misread subject name, remove a subject that was incorrectly included, add a subject the AI missed, correct a branch name, and correct a semester number. Only once the Admin explicitly confirms/saves this reviewed structure does it get written into the real `curriculum_subjects` table (and the corresponding `curriculum_uploads` row's `extraction_status` becomes `confirmed`). This mirrors the same "AI drafts, a human confirms before it becomes real data" principle already used elsewhere in this project for AI-assisted flows, and exists because syllabus PDF formatting varies enough that blind trust in extraction accuracy would produce a materially wrong curriculum for that college — which would then propagate incorrect information all the way through to what students eventually see.

### 2.5 Re-uploading / updating a curriculum later
Colleges update their curriculum periodically (new electives added, subjects renamed, semester restructuring). Support a college uploading a new curriculum document later, which should go through the exact same extraction-and-review flow as the first upload, producing a new `curriculum_uploads` row. Decide and implement one of two reasonable approaches for how this interacts with existing `curriculum_subjects` data and anything already built on top of it (subject selections, approved resources — see later parts): either (a) treat each new confirmed upload as fully replacing the previous curriculum for that college, requiring the Admin to be clearly warned before confirming that this will affect existing TPO subject selections and resource curations tied to removed/renamed subjects, or (b) treat it as additive/mergeable, where the review step in 2.4 is also where the Admin reconciles the new extracted list against the existing one (matching likely-same subjects, flagging genuinely new or removed ones). Approach (a) is simpler to build correctly and is the recommended starting point given the complexity of a good merge experience; document clearly in your implementation which approach was taken.

## PART 3 — TPO Subject Selection ("Market Trend" Curation)

### 3.1 What the TPO sees
On the TPO's dashboard, add a new section, something like "Subject Focus" or "Curriculum Resources," scoped automatically to that TPO's own college and (if this project's existing TPO role is itself branch-specific, confirm this against how TPO accounts are currently modeled — if TPOs are not currently branch-specific, decide whether this new feature should introduce that concept, since it would make sense for an IT-focused TPO to primarily manage IT's subject list rather than every branch's) their relevant branch(es). Show every subject from `curriculum_subjects` for that college (and branch, if branch-scoping TPOs is adopted), organized by branch and semester exactly as extracted/confirmed in Part 2, in a clear browsable structure (e.g., expandable semester sections within each branch).

### 3.2 Selecting subjects worth curating resources for
Not every subject needs AI-curated resources — a TPO should be able to select a subset of subjects they consider currently relevant (worth calling this "market trend" selection per the original framing, or simply "prioritized subjects," whichever reads more naturally in the actual UI copy) rather than being forced to generate resources for every single subject in the curriculum, most of which a TPO would have no real opinion on. Implement this as a simple toggle/checkbox per subject in the browsable structure from 3.1, with a clear call-to-action once one or more subjects are selected (e.g., a "Find resources for selected subjects" button) that kicks off the AI curation process described in Part 4 for exactly the subjects chosen — not for the whole curriculum.

### 3.3 Re-selecting or adding more subjects later
A TPO should be able to return to this screen at any time and select additional subjects beyond their initial choices — this is not a one-time, locked-in decision. Subjects already selected and already curated (see Part 4) should show their current status here too (e.g., "Curated — 3 resources," "Awaiting your review," "Not yet selected") so the TPO has one place that shows the full picture of what's been done and what's still pending, rather than needing to check a separate screen to see review status.

## PART 4 — AI Resource Curation (Books, Articles, Educational Videos)

### 4.1 The pipeline, mechanically, reusing what already exists
This should reuse the exact same underlying combination already built for this platform's Career Insights feature: a web-search API call followed by a Groq call that processes and summarizes the search results into something structured and useful. For each subject a TPO has selected (Part 3.2), run a search (or a small number of separate searches — for example, one oriented toward finding a well-regarded book/textbook on the subject, one oriented toward articles/written explainers, one oriented toward free educational video content) and pass the results to Groq with a prompt instructing it to select the handful of best results and, for each one, produce: the resource's title, a direct link, a resource type classification (book, article, video), and a short, original one-to-two sentence summary of what it covers and why it's useful — written by the AI in its own words, not copied text from the source.

### 4.2 Copyright and content-integrity rules — read carefully, this matters more here than almost anywhere else in this project
The AI must only ever produce a link plus an original summary written in its own words. It must never reproduce actual excerpted text, paragraphs, or substantial content from the book, article, or any source material it finds — this is a hard rule that applies with extra force here specifically because this feature operates at real scale (potentially dozens of subjects across many colleges, each generating multiple resource entries), unlike a one-off single answer, so a systemic pattern of over-copying compounds into a much larger problem than an isolated instance would. When summarizing a book, describe its general subject coverage and reputation/relevance in the AI's own words (e.g., "a widely used introductory textbook covering normalization, transactions, and indexing") rather than anything resembling reproduced jacket-copy or excerpted chapter text. Do not link to or recommend clearly pirated/unauthorized copies of copyrighted books found through search results — prefer links to official publisher pages, legitimate retailers, official course platforms, or genuinely open-access/free educational material.

### 4.3 Being honest about what "high quality" or "highly rated" actually means here
A general web-search API does not give reliable, verified quality signals the way a platform-specific API with real engagement metrics would (for example, an actual YouTube Data API call could return real view counts and like ratios for a video; a generic web search cannot). Do not present curated resources to TPOs or students with language implying verified ratings or rankings unless the underlying data genuinely supports that claim. What is honestly achievable is Groq's judgment of relevance and apparent credibility based on search result content, titles, and source reputation — describe this accurately in whatever UI copy accompanies these resources (e.g., "AI-recommended" rather than "top-rated" or "highest-rated"), so the feature's claims match what it can actually verify.

### 4.4 Caching — do not regenerate on every view
Once a subject's resources have been curated (and, per Part 5, approved), store them persistently — create a table such as `curated_subject_resources`: `id`, `subject_id` (referencing the specific `curriculum_subjects` row), `resource_type` (book/article/video), `title`, `link`, `ai_summary`, `generated_at`, `approval_status` (see Part 5). Do not re-run the search-and-curate pipeline every time a TPO or student views a subject's resources — only run it when a TPO explicitly requests curation for a newly selected subject (Part 3.2), or when a TPO explicitly requests a refresh of an already-curated subject's resource list (a "Refresh recommendations" action, useful if a TPO isn't satisfied with what AI found the first time, or simply wants an updated list after enough time has passed that better material might now exist). This mirrors the same caching discipline already applied to this platform's Career Insights feature, for the same reasons: cost and latency.

## PART 5 — TPO Review and Approval

### 5.1 Why approval is required, not optional, for this first version
AI-curated external links and summaries should not go directly in front of students without a human checking them first, for the same reason this project already requires human review of AI-extracted curriculum data (Part 2.4) — broken links, subtly irrelevant picks, or a summary that misrepresents what a resource actually covers are more visibly embarrassing and harder to auto-correct here than, say, an imperfect AI-generated quiz question would be, since there's no auto-grading safety net catching a bad recommendation the way there might be for a scored test.

### 5.2 What the review screen looks like and does
For each subject a TPO has requested curation for, once the AI pipeline (Part 4) completes, show the TPO a review screen listing every candidate resource returned (grouped by type — books, articles, videos), each with its title, link (clickable, so the TPO can actually open and check it), and AI-written summary. Give the TPO the ability to approve or reject each resource individually (not just approve/reject the whole batch at once, since a curated set of five resources might have four good ones and one clearly bad one) — implement this as a simple per-item approve/reject control, with only approved items ultimately becoming visible to students (Part 6). Optionally, but recommended if it's not significant extra effort, allow the TPO to lightly edit an AI-written summary before approving it, in case the summary is directionally correct but phrased in a way the TPO wants to adjust — this is a small addition that meaningfully increases trust in the feature without much implementation cost.

### 5.3 What happens to rejected resources
A rejected resource should not simply disappear with no trace — store its rejected status rather than deleting the row, so that if the same subject's resources are refreshed later (Part 4.4's "Refresh recommendations"), the system has a record of what was already reviewed and rejected before. Whether to feed this rejection history back into future AI curation attempts (e.g., instructing Groq to avoid resurfacing something already rejected for this subject) is a reasonable future enhancement, not a requirement for this first version — but at minimum, do not silently delete rejection history, since it has clear future value and costs nothing to retain.

## PART 6 — Student-Facing Display

### 6.1 What a student sees and how they get there
On the student's existing Resources page, the subject-based curriculum resources described in this document should be presented as a distinct, clearly organized section — reachable, per your own framing, by a student clicking a subject like "DBMS" and seeing the curated, approved set of books, articles, and videos for it, organized by resource type within that subject's page (a books section, an articles section, a videos section), each showing its title, a link the student can open, and the AI-written summary explaining what it covers. Only ever show subjects and resources belonging to the student's own college (standard college-scoping, exactly like every other feature in this project) and, within that, only resources with `approval_status = approved` from Part 5 — a rejected or not-yet-reviewed resource must never be visible to a student under any circumstance.

### 6.2 How this coexists with the existing flat Resources library
This new curriculum-driven, subject-organized resource system is a genuinely different organizing structure from the existing flat Resources library (which is organized by topic-pill and content-type, not by branch/semester/subject) described at the start of this document. Do not attempt to force-merge these into one single list — instead, present them as two clearly distinct, separately-labeled sections on the student's Resources page (for example, something like "Study material" for the existing flat library, and "By subject" or similarly clear labeling for this new curriculum-driven section), so students understand they are two different ways of finding material, not a single confusing combined list with two different organizing logics fighting each other.

### 6.3 The correction to the earlier hardcoded branch-pill work — implement this now, as part of this task
Earlier work on the existing flat Resources upload form (used by TPO/Admin to add resources to that older, flat library) added a fixed set of "Applicable branches" pill buttons: All branches, IT, CS, Mechanical, Civil, Electrical. This must now be corrected: replace that hardcoded pill list with pills generated dynamically from the actual branch names present in that specific college's `curriculum_subjects` table (distinct branch_name values for that `college_id`), plus an "All branches" option exactly as before. If a college has not yet uploaded and confirmed a curriculum (Part 2), this pill row should gracefully fall back to just showing "All branches" as the only option (since there is no per-college branch data yet to generate pills from), rather than erroring or showing a broken empty control. This is not an optional nice-to-have — it is the direct, necessary consequence of Part 1.4's stated principle, and leaving the old hardcoded pills in place after this feature exists would be a genuine inconsistency in the finished system, not a stylistic choice.

## PART 7 — Full End-to-End Flow Summary (for verification, restated plainly)

1. College Admin uploads a curriculum document.
2. AI extracts a draft structure of branches, semesters, and subjects from it.
3. College Admin reviews and corrects that draft, then confirms it — this becomes real, stored, per-college curriculum data.
4. TPO (for their college, and branch if branch-scoping is adopted) browses their real subject list and selects the subjects worth focusing on.
5. For each selected subject, AI searches the web and curates a shortlist of books, articles, and free educational videos, each with a link and an original AI-written summary — never reproduced source content.
6. TPO reviews the AI's curated shortlist per subject and approves or rejects each resource individually.
7. Only approved resources, for the student's own college, become visible on the student's Resources page, organized by subject, alongside (not merged with) the existing flat Resources library.
8. The earlier hardcoded branch-pill list on the older flat Resources upload form is replaced with branch pills generated dynamically from this same per-college curriculum data.

## PART 8 — Explicit Non-Goals for This First Version

Stated clearly so implementation doesn't drift into unscoped extra work: this first version does not need to support file formats beyond PDF (DOCX support is optional, not required); does not need to support merging/reconciling a re-uploaded curriculum against an existing one (Part 2.5's simpler replace-and-warn approach is sufficient for now); does not need to feed resource-rejection history back into future AI curation prompts (storing rejection history is required, using it to influence future AI behavior is not, for this version); and does not need to verify or display real engagement/rating metrics for curated resources (Part 4.3's honest "AI-recommended" framing is sufficient, integrating a dedicated video-platform API for real view/rating data is a reasonable future enhancement, not part of this task).
